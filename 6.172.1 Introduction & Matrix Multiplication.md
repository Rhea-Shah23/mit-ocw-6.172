**Why Performance Engineering?**
- Many software properties are much more important than performance
	- Performance is the currency of computing 
		- "buy" needed properties by sacrificing performance 
- Earlier: performance engineering was common and needed because machine resources were severely limited 
	- "Premature optimization is the root of all evil"
	- Until 2004: rely on hardware improvements for performance improvements (moore's law, dennard's scaling)
- Solution? Introduce parallelism:
	- Multiple processing cores per chip 
	- Performance was no longer "free"
		- Had to do parallel programing to optimize performance 
		- Software must adapt to utilize hardware capabilities 
- How can we write software to utilize hardware?

*Interpreters:*
- Reads, interprets, and performs each program statement and updates the machine state 
- Support high-level programming features at the cost of performance 
	- Versatile, but slow 
- Loop: interpret statement, perform statement, update state, read next statement...

*JIT Compilation:*
- Recover some of the performance lost by interpretation 
- When code is first executed, it is interpreted 
- Keeps track of how often the various pieces of code are executed 
- Whenever some piece of code executes sufficiently frequently, gets compiled to machine code 
- Future executions of that code use more efficient, compiled version 

- Loop Order: change order of loops without affecting its correctness 
	- Affects cache locality --> can be used to optimize performance 

*Cache Lines:*
- Each processor reads and writes main memory in contiguous blocks, called cache lines 
- Previously accessed cache lines are stored in smaller memory (cache) that is near processor 
- Cache Hits: accesses to data in cache --> fast 
- Cache Misses: accesses to data not in cache --> slow 
	- Restructure computation to avoid cache misses 

- Interchance Loops: 
- Change compiler flags
	- ask it to optimize 
- Why low performance? Not using all cores!! 
	- Parallelize the inner and/or outer loop 
- Minimize cache misses: blocks that fit in cache (tiling) 
	- Find tiling size: experiment!
- Recursive parallel matrix multiplication 
	- Bad result:
		- Bad base case --> a lot of fxn overhead --> poor performance 
		- Better base case
			- Standard algo for base case(s) + Parallelize for non-base cases = good performance 
*Vector Hardware:*
- Process data in a single-instruction stream, multiple data-stream (SIMD) fashion 
	- each vector reg holds multiple words of data 
	- operate on the data as one chunk of vector data, all have to do same thing, difference is index in memory 
- Clang/LLVM can produce vectorization report
